# RiskLens Dashboard: Guide to All 10 Tabs

This guide describes the dashboard as it is currently implemented in
`dashboard.py`. The dashboard has **10 tabs**. Some tabs use the main dataset
directly, while others need a results file generated by a separate script.

## Before exploring the tabs: what does “High” mean?

In the main dataset, Low, Medium, and High are categories made from how many
commits changed a file in the repositories' recorded history. With the current
training dataset, the boundaries are Low at 7 revisions or fewer, Medium above
7 and up to 27, and High above 27.

These categories mean **historical change activity**. They do not mean a file
is buggy, will have a bug, or is guaranteed to change again. The dashboard
sometimes uses the short word “risk” in a label, but the careful interpretation
is historical change-proneness, not defect risk.

The main dashboard loads `full_merged_dataset.csv` and fits an interactive
Random Forest when it starts. This dashboard model uses a stratified random
75%/25% file split for its demonstration and is cached while the Streamlit
session is running. Separate analysis scripts create saved evaluation results,
held-out predictions, and the model files used by the new-repository scorer.
Therefore, not every tab is displaying predictions from the same trained
model or evaluation method. Each tab below identifies which one it uses.

## At a glance

| # | Tab | Main purpose | Additional result file needed? |
|---:|---|---|---|
| 1 | Predict a File's Change Activity | Try a dataset file or custom measurements and inspect one prediction | No |
| 2 | Compare Two Files | Compare two files' measurements, predictions, and explanations | No |
| 3 | High Change-Proneness Leaderboard | Rank files using predictions from models that held out each repository | Yes: output from `master_analysis.py` |
| 4 | Model Insights | Show the interactive model's classification report and overall feature importance | `master_results.json` for the saved importance chart |
| 5 | Explore Dataset | Filter and browse the rows and input metrics | No |
| 6 | Bayesian Network | Show a learned metric-relationship graph and compare its result with the Random Forest | Yes: output from `bayesian_network_analysis.py` |
| 7 | Robustness Checks | Examine correlations, feature importance checks, feature removal, and feature groups | Yes: output from `feature_robustness_check.py` |
| 8 | SonarQube Comparison | Browse matched SonarQube measures and compare SonarQube feature sets | Yes: outputs from `sonarqube_file_comparison.py` and `sonarqube_vs_model.py` |
| 9 | Cross-Repository Evaluation | Show how a model performs on an entire repository it did not train on | Yes: output from `master_analysis.py` |
| 10 | Score a New Repo | Display a CSV report produced by scoring another local Git repository | Yes: output from `score_repo.py` |

## Tab 1 — Predict a File's Change Activity

### What it is for

This is the interactive “try a prediction” screen. It lets you see what the
dashboard's currently trained Random Forest predicts from the nine metrics
for one file.

### Two ways to provide a file

**Pick an existing file.** Choose one of the five repositories, then choose a
file from that repository. The dashboard fills the model inputs from that
file's row in `full_merged_dataset.csv`. It also shows the actual historical
category and the file's recorded revision count, so you can compare the
model's answer with the category already in the dataset.

**Enter custom metric values.** Use sliders to create a hypothetical file
profile. The sliders cover:

- Average and maximum complexity
- Total lines of code and function count
- Maintainability index
- Number of authors and code age in days
- Coupling partner count and average coupling degree

The starting value for each slider is the dataset median, limited to the
slider's displayed range. Changing a slider lets you explore how the trained
model reacts while other inputs stay fixed. These values are a “what if”
experiment, not measurements from a real file unless you enter values taken
from one.

### What the result shows

After selecting a dataset file, click **Predict Risk**. For custom values,
the prediction updates automatically. The page displays:

1. A predicted Low, Medium, or High historical-activity category.
2. For a real dataset file, the actual historical label and revision count,
   plus whether the model prediction matches that label.
3. A bar chart with the model's probabilities for Low, Medium, and High.
4. A SHAP chart explaining which input measurements pushed the prediction
   toward or away from the predicted category.

In the SHAP chart, red bars push the output toward the category being
explained; blue bars push away from it. They explain the model's calculation,
not causes of file changes.

### Important distinction

This tab uses the dashboard's random-file-split model. It is useful for
demonstrating the model and exploring hypothetical measurements. It is not
the strict “new repository” test. For a whole-repository holdout, see Tab 9.
For scoring an external local repository with the saved full/static models,
see Tab 10.

## Tab 2 — Compare Two Files

### What it is for

This screen places two files side by side so you can inspect how their
measurements and model explanations differ.

### How to use it

Choose a repository and file for File A, and independently choose a repository
and file for File B. The two files can come from the same repository or
different repositories. Click **Compare** to calculate and display the
results.

### What it shows

For each selected file, the page displays:

- The interactive dashboard model's predicted historical-activity category.
- The file's actual dataset category and historical revision count.
- A table comparing all nine input measurements.
- A separate SHAP chart for each file, explaining that file's predicted
  category.

This is useful for questions such as “Why did the model put these files in
different categories?” You can look for differences in size, complexity,
maintainability, number of authors, age, or coupling.

### How to interpret it

The side-by-side measurements are descriptive. The SHAP charts say which
measurements influenced each prediction within this fitted model. They do not
show that one file's measurements caused its changes, nor that a file with a
High category has a defect. As with Tab 1, these are interactive-model
predictions, not the repository-held-out predictions shown on Tab 3.

## Tab 3 — High Change-Proneness Leaderboard

### What it is for

This tab lists up to 15 files with the highest model score for the High
historical-change category.

### Which predictions it uses

Unlike Tabs 1 and 2, this leaderboard uses
`repo_holdout_high_probability` and `repo_holdout_prediction` stored in the
merged dataset. These predictions are generated by leave-one-repository-out
evaluation: the model that produced a file's score was trained without that
file's entire repository.

### What it shows

The ranked table includes:

- Repository and file path
- The prediction made while that repository was held out
- The model's High-category score
- The file's historical category and revision count
- Distinct author count and maximum complexity

Below the table, a bar chart shows the **average held-out High-category score
per repository**. It is a repository-level summary of model outputs, not a
comparison of bug rates.

### When results are missing

If the merged dataset has no held-out prediction columns, the tab asks you to
run `python master_analysis.py`. That script writes the held-out predictions
back into `full_merged_dataset.csv`.

### Important interpretation

The leaderboard is a ranking of files the classifier considers most like the
High historical-change group. It is not a list of confirmed problem files and
does not predict future defects. Each held-out score avoids training on the
same repository, which makes it a more demanding test than an ordinary random
file split, but the underlying measurements and labels still describe the
repositories' complete recorded histories.

## Tab 4 — Model Insights

### What it is for

This tab gives a compact summary of how the dashboard's interactive
Random Forest classified its held-out random-file test sample and which
measurements ranked highest in the saved master analysis.

### What it shows

**Classification report.** The text report gives precision, recall, and F1
for each of Low, Medium, and High, along with overall averages. In ordinary
language:

- Precision asks: among files assigned to a category, how many truly had that
  dataset category?
- Recall asks: among files that truly had a category, how many did the model
  find?
- F1 combines precision and recall into one balance score.

This report comes from the interactive model trained on a stratified random
75% of the files and evaluated on the remaining 25%.

**Overall feature-importance chart.** If `master_results.json` exists, the
chart displays the importance ranking saved by `master_analysis.py`. The
information box names the two highest-ranked inputs from that saved analysis.
Feature importance indicates how much a feature helped the trained forest
make classifications; it does not say that the feature causes change activity.

### When saved results are missing

If `master_results.json` is missing, the classification report from the
interactive model still appears, but the saved importance chart does not.
Run `python master_analysis.py` to produce the JSON results.

### Important distinction

The classification report here and the saved importance chart are related but
not necessarily calculated from the exact same fitted model: the report uses
the model fitted by the dashboard, while the chart uses the saved master
analysis. Read their labels and method descriptions before treating them as
one result.

## Tab 5 — Explore Dataset

### What it is for

This is a browsable view of the merged file-level dataset. It is useful for
checking which rows and values are behind the other analysis tabs.

### Filters and columns

You can filter the rows by:

- One or more repository names
- One or more historical categories: Low, Medium, or High

The table then shows repository, file path, category, revision count, and the
nine model features. A caption reports how many rows are displayed and how
many rows exist in the loaded dataset.

### What it does not do

This is a data-inspection view, not a model evaluation. Filtering the table
does not retrain the model or change its predictions. The category still
comes from the recorded revision-count labels.

## Tab 6 — Bayesian Network

### What it is for

This tab displays a second kind of model: a Bayesian network. Its purpose is
to show a graph of probabilistic relationships among the measured variables,
alongside a performance comparison with the Random Forest.

### What it shows

When its saved output files are available, the page displays:

1. The learned network image.
2. A table of the network's learned edges (the arrows/relationships in the
   graph).
3. The Random Forest macro F1 from `master_results.json`, when available.
4. The Bayesian network's macro F1, accuracy, and row count from its saved
   result file.
5. A short explanation of why the project includes both a prediction-focused
   forest and a graph-based model.

The graph structure is produced by a data-driven search rather than manually
drawing every arrow. The method tries possible graph connections and keeps a
structure that fits the data under its scoring rule.

### When results are missing

Run `python bayesian_network_analysis.py` to generate the network graph and
its results JSON. The tab warns if either file is absent.

### Important interpretation

An arrow in this learned graph is a relationship inferred by the algorithm
from the available data. It should **not** be read as proof that one software
metric causes another, or as a proven causal explanation of future changes.
The target remains historical revision activity, and any performance score
depends on the evaluation method saved by the analysis script.

## Tab 7 — Robustness Checks

### What it is for

This tab checks whether conclusions about the nine model features are
supported by more than one view of the data. It compares **all nine features**
throughout; author count is discussed later as one notable example, rather
than being the focus of the whole tab. It reads
`feature_robustness_results.json`, generated by
`python feature_robustness_check.py`.

At the top, three summary cards identify the feature with the strongest
absolute association with revision count, the feature whose shuffling caused
the largest mean held-out F1 drop, and the feature whose removal caused the
largest five-fold F1 drop. These are selected from the generated results, so
the highlighted feature can change if the analysis is rerun on updated data.

### The four checks

**1. Association with revisions.** A chart and table show Spearman
correlations between each feature and revision count. This is a direct
relationship check and does not train a model. A positive value means that
higher ranks of the feature tend to go with higher ranks of revision count;
a negative value means they tend to move in opposite directions. Correlation
does not establish cause and effect.

**2. Held-out shuffling (permutation importance).** The analysis shuffles one
feature's values among held-out files and observes how macro F1 changes. If
performance drops, the model was using that feature on those examples. The
chart shows the average change and its variation across repeated shuffles.
Blue indicates the mean drop was larger than the shuffle variation in this
analysis; gray means it was not. This is a useful diagnostic, not a formal
statistical proof.

**3. Remove one feature at a time.** The table reports five-fold macro F1
after removing each feature and the change from the all-feature result. A
substantial decline suggests that the removed input supplied information the
remaining features did not fully replace. A small decline does not prove a
feature is useless: similar or overlapping measurements can substitute for
one another.

**4. Compare groups of features.** The chart/table compare macro F1 for
selected combinations, including static code measures alone, static measures
plus age, static measures plus authors, static measures plus authors and age,
and all nine features. This helps show whether history-derived measurements
add information beyond code structure alone.

### Author count as one example

The final section uses author count as a focused example of how to interpret a
feature that stands out:

- Correlation between author count and revision count
- Average held-out F1 change when author values are shuffled
- Five-fold F1 when author count is removed, compared with all features

The text explains why authors can rank strongly: files with more recorded
changes have had more chances to accumulate distinct contributors. Authors
and revisions are both extracted from the same history, so this association
is expected and is not proof that adding authors causes more changes.

### Limitations shown in the tab

The checks use the existing historical dataset. They do not establish that
author count or any other feature predicts future revisions from today's
information, nor that a feature predicts defects. The random-file split in
the permutation check can include files from the same repositories in both
training and test sets; for the stricter repository test use Tab 9, and for
the time-based experiment use the separate temporal-validation outputs.

If the JSON file is missing, run `python feature_robustness_check.py`.

## Tab 8 — SonarQube Comparison

### What it is for

This tab puts per-file SonarQube measures beside the project's repository
metrics and model predictions. It reads `file_level_comparison.csv`, produced
by `sonarqube_file_comparison.py`.

### Matched files and summary cards

The model dataset and SonarQube export are joined by repository and
normalized file path. A “matched file” is a file that was successfully
identified in both sources, so both tools' rows refer to the same repository
file. The page reports the number of matched files, represented repositories,
and files whose selected prediction/category is High.

If the file includes repository-held-out prediction columns, those predictions
are selected. If it only has the older risk-label data, the tab uses that
instead and warns that a more current comparison should be generated.

### Charts and tables

**Findings grouped by category.** Where the required columns exist, the page
summarizes SonarQube code smells, bug findings, cognitive complexity, and
duplication density within each model-predicted category. For each measure it
can show count, median, and mean. Code smells and bugs are not inputs to the
nine-feature model. The table is a descriptive summary of SonarQube values
within the model-predicted groups.

**Matched file details.** Filter the table by repository and selected
category. Available columns include file path, historical category, held-out
actual and predicted categories, High score, revision count, SonarQube
complexity/cognitive complexity/code smells/bugs/duplication/ncloc, and
Lizard maximum complexity.

The current dashboard text says missing code-smell, bug, and duplication
measures are treated as zero reported findings in this comparison file;
other missing measures remain unavailable. A zero or missing measurement
should be interpreted according to how the SonarQube export was generated,
not automatically as proof that a file has no quality issue.

### What it can tell you

This tab helps explore whether model categories and SonarQube signals tend
to overlap in the matched files. SonarQube and RiskLens have different
targets: SonarQube reports findings under configured code rules, whereas the
RiskLens category is based on revision activity. The tab does not calculate
bug-prediction accuracy.

If comparison data is missing, start/scan the SonarQube projects and run
`python sonarqube_file_comparison.py`. If the SonarQube server is unavailable,
the script may be able to reuse cached measures with
`python sonarqube_file_comparison.py --use-cached`, if the required cached
data exists.

### Does adding SonarQube measurements improve classification?

This section is also part of Tab 8. It reads
`sonarqube_vs_model_results.csv`, generated by
`python sonarqube_vs_model.py`, and asks whether SonarQube measurements help a
Random Forest classify the historical revision categories.

It compares five feature groups on the same matched files and the same five
stratified data splits:

1. SonarQube measurements only.
2. Static code measurements only.
3. Repository-history measurements only.
4. The existing nine model features.
5. The existing nine features plus SonarQube measurements.

The section shows the feature group with the best average macro F1, average
and per-category F1 values, a bar chart with variation between splits, and a
paired fold-by-fold comparison of the existing nine features against the
combined set. A positive paired change means SonarQube improved that split;
a negative change means it reduced the score.

The summary check asks whether the average paired improvement exceeds the
variation across the five splits. This is a descriptive stability rule, not a
formal statistical test. For the current results, the existing nine features
scored about **0.784** mean macro F1, while adding SonarQube scored about
**0.783**. The average paired change was about **−0.001**, so adding SonarQube
did not improve the overall score in this experiment.

This comparison is about classifying historical revision activity. It does
not establish whether SonarQube finds bugs or whether the model detects
defects. If its results CSV is missing, run `python sonarqube_vs_model.py`
and refresh the dashboard.

## Tab 9 — Cross-Repository Evaluation

### What it is for

This tab answers: “If the model has never seen one of these repositories
during training, how well does it classify files from that repository?”

### How the test works

The analysis holds out one entire repository at a time. It trains using the
other four, then predicts files from the held-out repository. It repeats this
for each of the five repositories. No file from the held-out repository is
used to train that fold's model.

For each fold, the Low/Medium/High revision thresholds are calculated from
the four training repositories and applied to the held-out repository. This
means a held-out repository's category proportions can differ from the
training set's proportions.

### What it shows

The summary cards report:

- Macro F1 across all held-out file predictions
- Accuracy across all held-out file predictions
- Mean macro F1 when averaging the five repository-specific results equally

The per-repository table shows each repository's file count, macro F1,
accuracy, and the training cutoffs used for that fold. This makes it possible
to see that results vary across projects rather than relying on one average.

### What it tests—and does not test

This is a stronger test of transfer between projects than randomly splitting
individual files. However, the feature values are whole-history summaries and
the labels are also based on whole-history revisions. It is **not** a test of
whether today's metrics forecast future changes. The temporal validation is
the separate time-based experiment.

If `generalization_results.json` is missing, run
`python master_analysis.py` to regenerate the evaluation and held-out dataset
predictions.

## Tab 10 — Score a New Repo

### What it is for

This is the dashboard view for a separately generated report about another
team's local Git repository. It does not scan or extract the repository inside
Streamlit. The command-line tool does the analysis first; the dashboard then
reads its CSV.

### Generate the report

First create or refresh the trained model files:

```powershell
python master_analysis.py
```

Then score a local repository:

```powershell
python score_repo.py --repo "C:\path\to\team-repo" --out risk_report.csv
```

Optional test-file exclusion:

```powershell
python score_repo.py --repo "C:\path\to\team-repo" --out risk_report.csv --exclude-tests
```

The repository must already exist locally and contain Git history. The scorer
does not clone repositories or contact a network service. It measures Python
source files using Lizard and Radon and reads available Git history using
PyDriller. The report includes tracked and non-ignored untracked Python files.

### Load the report into the tab

The tab first offers a CSV upload. If no upload is selected, it looks for
`risk_report.csv` beside `dashboard.py`. If neither is available, it explains
how to generate one.

The loaded report must contain file path, predicted category, High-class
score, revisions-before count, selected model, static-model flag, and three
plain-language reason columns. The tab reports an error if these expected
fields are absent or the CSV cannot be read.

### Ranked table

The report is sorted from highest to lowest High-class score. It displays:

- File path
- Predicted historical-activity class
- Probability assigned by the model to the High historical-activity class
- Number of commits touching the file in the available local history
- Whether the full nine-feature or static-only model was used
- Three largest SHAP reasons for the High-class score

Files with fewer than five commits touching them use the **static-only model**
and are flagged. This avoids relying on very sparse author/age/coupling
history for those files.

### Selected-file explanation

Choose any report row to display its predicted category, High-class score,
model used, and its three leading plain-language reasons. A horizontal SHAP
bar chart shows the High-class contribution from each available input:

- Red bars push the High-class score up.
- Blue bars push it down.

For a file scored by the static-only model, history-only feature contributions
are absent because that model does not use those features. SHAP describes
how the model reached its score; it does not establish a cause.

### Training cutoffs and relative scores

The tab can show the original training revision cutoffs included in the
report. Those training cutoffs are kept fixed; the scorer does not calculate
percentiles from the new repository. Thus a new team's scores are relative
to patterns learned from the five training repositories. A “70% High score”
is not a statement that there is a 70% chance of a bug or future change.

## How to understand the dashboard as a whole

The tabs serve three different jobs:

1. **Explore the trained classifier:** Tabs 1, 2, 4, and 5 let you inspect
   its inputs, predictions, and dataset.
2. **Check evidence and limitations:** Tabs 3, 6, 7, 8, and 9 provide
   held-out rankings, a second model view, robustness checks, SonarQube
   comparisons, or evaluation across repositories.
3. **Apply the model to a local project:** Tab 10 displays an externally
   generated repository report.

Do not interpret all category labels as defect labels. Tabs 1–9 principally
relate to historical revision activity (with Tab 9 explicitly testing
repository transfer); Tab 10 applies the saved classifier to new files using
training-derived categories. Future revision activity is evaluated by the
separate temporal-validation experiment, not by the original historical
classification tabs. None of these tabs, as currently implemented, proves
future bug prediction.
